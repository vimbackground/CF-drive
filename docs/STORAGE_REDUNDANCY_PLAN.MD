# CF-drive 双模式存储与节点归集正式方案

状态：架构决策已确认，待分阶段实施  
适用范围：当前单主控、多受控存储节点架构  
暂不包含：多节点纠删码/类 RAID5、任意节点之间的通用主控角色转换、自动选主

## 1. 决策摘要

系统提供两种全局存储模式，由管理员在主控后台选择：

1. **Stripe 容量模式**：把主控和多个受控节点组合为统一容量池。每个物理分片只保存一份，容量接近各节点可用容量之和，但任一节点永久丢失都可能使部分文件不可恢复。
2. **Mirror 容灾模式**：选择两个位于独立 Cloudflare 账号/故障域的实例组成固定镜像对。文件数据和必要控制面恢复状态各保存两份；任一实例或账号失效后，可在另一个实例执行灾备接管并重新绑定原域名。

Stripe 模式同时提供受控节点归集功能：在节点可访问且主控容量足够时，将该节点的有效分片安全迁移到主控 R2，完成后允许删除节点。

Mirror 模式中的灾备接管是固定镜像对的专用恢复流程，不扩展为任意主控/受控节点互换，也不提供自动选主。

## 2. 目标与非目标

### 2.1 目标

- 允许用户在“最大化容量”和“单故障域容灾”之间明确选择。
- 所有文件都能从 manifest 判断保护模式、物理位置、校验状态和布局版本。
- Mirror 模式容忍镜像对中任一 Worker、R2、D1 或 Cloudflare 账号不可访问。
- Mirror 灾备接管后，重新绑定原域名即可继续访问原目录和文件；使用原域名生成的文件路径和分享 URL 保持不变。
- Stripe 节点可以通过可暂停、可恢复、可审计的迁移任务归集到主控。
- 模式切换和节点删除不得静默降低已有文件保护等级。

### 2.2 非目标

- 本阶段不实现 `2+1`、`4+2` 等纠删码。
- 本阶段不实现自动故障检测后自动切换 DNS 或自动晋升。
- 本阶段不允许任意受控节点成为主控。
- 不承诺正在进行的上传、登录会话、短期授权 Cookie 在灾备接管时不中断。
- 不承诺 DNS/自定义域名变更立即在所有客户端生效。

## 3. 术语与故障域

- **实例**：一套 Worker、D1 和 R2 绑定。
- **故障域**：可能被同一事件同时影响的一组资源。为防止 Cloudflare 账号被禁用，Mirror 两端必须属于不同 Cloudflare 账号，并使用独立凭据。
- **主控 A**：正常状态下唯一提供文件管理和写入的实例。
- **镜像 B**：Mirror 模式下的固定灾备实例。正常状态下不提供普通网盘写入，只接收镜像数据和控制面恢复状态。
- **集群 ID**：镜像对共享且在灾备接管后保持不变的稳定身份。
- **布局版本**：manifest 对应的数据放置协议版本。
- **恢复包**：在 B 上保存的、可恢复文件树和管理状态的加密控制面快照/日志。

同一账号中的两个 Worker 不视为两个独立故障域，不能标记为“账号级容灾已就绪”。

## 4. Stripe 容量模式

### 4.1 数据布局

- 主控 A 和所有 `active` 受控节点共同组成容量池。
- 每个逻辑分片只有一个物理位置。
- 分配器根据节点可用容量、权重、健康状态和当前负载选择节点。
- 同一个文件可以包含分布于多个节点的分片。
- manifest 必须记录 `layoutVersion`、`mode: stripe`、分片摘要和唯一 placement。

逻辑可用容量约为各节点可用容量之和，但不对节点永久丢失提供恢复保证。后台必须持续显示“容量优先，无节点级冗余”的风险标识。

### 4.2 故障行为

- 短暂网络故障：对原节点有限重试；节点恢复后文件恢复可读。
- 节点永久丢失：引用该节点任一分片的文件标记为 `unavailable`，禁止把缺失文件误报为完整。
- 主控故障：Stripe 模式没有镜像控制面和完整数据副本，不承诺由受控节点直接接管。

### 4.3 节点归集

归集用于计划内退役、账号迁移、缩容或风险节点撤离，不能恢复已经丢失的数据。

状态机：

`active → draining → copying → verifying → switching → observing → retired`

执行规则：

1. 进入 `draining` 后立即停止向源节点分配新分片。
2. 主控以 manifest 引用为权威集合，不直接把源节点所有对象都视为有效文件。
3. 创建持久迁移任务，按文件和分片分批执行，保存 checkpoint、重试次数、字节进度和错误信息。
4. 将分片以流式方式复制到主控 R2，不把完整大文件载入 Worker 内存。
5. 使用源分片摘要、目标摘要和长度进行校验。
6. 使用 manifest 版本号/CAS 原子切换 placement；并发覆盖或删除必须使旧迁移任务失效或重新排队。
7. 切换后进入观察期。读取只使用新位置，旧位置暂不删除。
8. 确认所有 manifest 对源节点零引用且观察期结束后，删除源分片并把节点标记为 `retired`。

启动归集前必须计算主控可用空间。主控容量不足时拒绝启动，并显示所需空间、可用空间和缺口。归集过程中源节点不可访问时暂停任务，不删除任何已验证源数据。

## 5. Mirror 容灾模式

### 5.1 拓扑限制

- 第一版每个存储集群只允许一个固定镜像对：A+B。
- A、B 必须处于两个独立 Cloudflare 账号。
- 两端必须各自具备足以保存全部受保护数据的容量。
- Mirror 有效容量按两端较小的可用容量计算，不与其他 Stripe 节点容量叠加。
- 第一版不允许同一集群内部分文件 Stripe、部分文件 Mirror，避免用户误判保护范围。

### 5.2 数据布局与写入提交

manifest 使用 `mode: mirror`，每个逻辑分片记录两个 replica placement、各自摘要、状态和写入代次。

正常写入流程：

1. A 为逻辑分片生成稳定 `partId` 和 `generation`。
2. 数据流分别写入 A、B，物理 key 可不同，但必须关联相同逻辑分片。
3. 两端分别返回长度和内容摘要。
4. 只有两个副本都写入并通过校验后，A 才提交 manifest 和文件目录记录。
5. 提交失败时不发布文件；已产生的临时副本由后台垃圾回收。

第一版采用严格保护策略：当 B 不可用时，现有完整文件仍可从 A 读取，但停止新增和覆盖写入。管理员不得在未明确确认风险的情况下把系统长期降级为单副本写入。

### 5.3 读取与修复

- 正常优先读取本地 A 副本。
- A 中某个副本校验失败时自动读取 B，并把文件标记为需要修复。
- B 恢复后，后台根据健康副本重建缺失或损坏副本。
- 定期 scrub 对比 manifest、长度和摘要，不依赖“对象存在”判断数据完整。
- 任一副本修复完成前，后台显示 `degraded`，不得显示“容灾正常”。

### 5.4 控制面恢复状态

只镜像 R2 数据不足以完成账号级灾备。B 还必须保存可重建控制面的恢复状态，至少包括：

- 集群 ID、布局版本和最新提交序号；
- 文件、目录与 manifest 元数据；
- 分享记录及保持原分享 URL 所需的签名材料；
- 节点、镜像关系、迁移任务和审计记录；
- 必要站点设置；
- 不包含可直接读取的管理员明文密码或节点明文密钥。

恢复状态采用“增量日志 + 周期完整快照”：

- 每次会改变用户可见状态的事务生成单调递增 `commitSequence`。
- A 在本地 D1 提交前/同一提交协议内，把加密增量发送给 B 并取得确认。
- B 保存最后确认序号和周期完整快照。
- 管理后台同时显示数据副本状态和控制面恢复点，二者都同步才标记 `protected`。

恢复包必须使用独立灾备密钥加密。灾备密钥或恢复密钥不得只存放在 A 所属 Cloudflare 账号中，应由管理员离线保存或放在独立密钥系统中。

### 5.5 灾备接管

本方案不做通用角色转换，只允许预先登记的镜像 B 执行固定灾备接管：

1. 管理员确认 A 已不可恢复或已被隔离。
2. 在 B 的本地恢复入口输入离线恢复凭据并执行 `PROMOTE` 确认。
3. B 校验恢复包完整性、提交序号、数据副本状态和集群 ID。
4. B 从最新完整快照和增量日志重建本地 D1。
5. B 生成新的主控任期 `controllerEpoch`，撤销旧 A 的写入凭据，并进入恢复主控模式。
6. 管理员把原自定义域名重新绑定到 B。
7. 使用原域名访问时，目录、文件路径和分享 URL 保持不变；客户端重新登录后继续使用。

为防止双主，B 不能仅因探测不到 A 就自动晋升。第一版必须人工确认；旧 A 恢复后也不能自动接受写入，必须先以更高 `controllerEpoch` 重新登记或清理。

这里的“无感继续使用”指业务数据、文件路径和基于原域名的链接连续；不包含正在进行的上传、旧登录会话和 DNS 传播时间。

## 6. 模式切换

模式切换不是配置字段即时生效，而是一个数据迁移任务。

### 6.1 Stripe → Mirror

1. 选择并验证两个独立账号实例 A、B。
2. 检查两端容量均能保存全部逻辑数据。
3. 暂停节点拓扑变更，建立 Mirror 恢复状态同步。
4. 后台扫描所有 manifest，为每个分片补齐第二副本和摘要。
5. 全量 scrub 通过后，把全局模式切换为 Mirror。
6. 未完成前后台显示 `converting_to_mirror`，不得显示容灾已启用。

### 6.2 Mirror → Stripe

1. 管理员确认将失去账号级单故障容灾。
2. 选择 Stripe 节点池和放置策略。
3. 将每个 mirror manifest 转换为单 placement，但保留旧副本观察期。
4. 全量引用检查通过后，再清理多余副本和恢复状态。

切换任务失败时，保持旧布局为读取权威，不允许出现一部分 manifest 已按新模式解释、另一部分仍按旧模式解释但后台显示完成的状态。

## 7. 数据模型

建议引入 manifest v2：

```json
{
  "type": "distributed-file",
  "version": 2,
  "layoutVersion": 1,
  "mode": "stripe",
  "generation": 12,
  "size": 1048576,
  "contentHash": "sha256:...",
  "parts": [
    {
      "partId": "...",
      "offset": 0,
      "size": 524288,
      "hash": "sha256:...",
      "replicas": [
        { "storageId": "...", "key": "...", "state": "healthy" }
      ]
    }
  ]
}
```

- Stripe 的 `replicas` 长度必须为 1。
- Mirror 的 `replicas` 长度必须为 2，且两个 `storageId` 必须属于不同账号故障域。
- v1 manifest 保持只读兼容，通过后台迁移逐步升级，不能原地改变 v1 字段语义。
- manifest 不保存节点明文连接密钥。

新增持久状态至少包括：

- `storage_policy`：当前模式、目标模式、保护状态、镜像对；
- `migration_jobs`：归集和模式转换进度；
- `replica_health`：副本最后验证、失败原因和 repair 状态；
- `control_commits`：控制面提交序号和镜像确认状态；
- `controller_epoch`：灾备接管后的单调主控任期。

## 8. 后台管理设计

存储设置页增加：

- 模式卡片：Stripe 容量优先 / Mirror 容灾优先；
- 当前总容量、有效容量、冗余开销和故障域数量；
- Mirror 两端账号/实例、数据同步状态、控制面恢复点和最近 scrub；
- Stripe 节点的“停止写入并归集到主控”操作；
- 迁移任务进度、速度、剩余字节、失败原因、暂停/继续/取消；
- `healthy / degraded / unprotected / migrating / recovery-ready` 状态；
- 灾备恢复说明和恢复凭据检查，不在普通页面显示密钥内容。

危险操作必须二次确认并清楚说明后果：Mirror 降级为 Stripe、删除最后一个健康副本、取消归集中已切换的任务、执行灾备接管。

## 9. API 边界建议

- `GET /api/storage-policy`：读取模式、容量和保护状态。
- `POST /api/storage-policy/convert`：创建 Stripe/Mirror 转换任务。
- `POST /api/storage-nodes/drain`：停止新分配。
- `POST /api/storage-nodes/consolidate`：创建归集任务。
- `GET /api/storage-jobs`：查询任务与 checkpoint。
- `POST /api/storage-jobs/:id/pause|resume|cancel`：控制任务。
- `POST /api/mirror/scrub`：启动副本校验。
- `POST /api/mirror/repair`：修复缺失副本。
- `GET /api/recovery/status`：读取恢复包和接管准备状态。
- `POST /api/recovery/promote`：在固定镜像 B 上执行人工灾备接管。

所有写接口要求管理员登录、同源 CSRF、防重放操作 ID，并记录审计事件。

## 10. 分阶段实施

### 阶段 1：统一布局基础

- manifest v2、稳定 storage ID、分片摘要、generation/CAS；
- v1 兼容读取和升级任务；
- 节点故障域登记与后台风险提示。

### 阶段 2：Stripe 归集

- 持久迁移作业；
- 流式复制、校验、原子切换和观察期删源；
- 容量预检、进度 UI、失败恢复与归集测试。

### 阶段 3：Mirror 数据面

- 双写提交、双副本 manifest、备用读取；
- degraded 状态、scrub、repair；
- Stripe ↔ Mirror 模式转换。

### 阶段 4：Mirror 控制面灾备

- 恢复状态增量日志和完整快照；
- 独立恢复密钥；
- 固定镜像接管、controller epoch、旧主控 fencing；
- 域名切换和完整灾备演练。

每一阶段独立验收；阶段 3 完成只能称为“文件数据双副本”，阶段 4 完成并通过演练后才能称为“账号级可接管容灾”。

## 11. 验收标准

### Stripe

- 多节点上传后的有效使用容量可以接近各节点容量之和。
- 任一分片始终只有一个权威 placement。
- 节点归集可中断后继续，重复执行不产生重复逻辑文件。
- manifest 切换前停止任务不会影响原文件读取。
- 归集完成并通过零引用检查后才能删除节点。

### Mirror 数据面

- 每个已提交文件的每个分片都有两个跨账号、摘要一致的副本。
- 任一端不可访问时，所有已提交文件仍能完整读取。
- 故障端恢复后可自动或人工 repair 至双副本健康状态。
- 第二副本未完成时文件不得显示为已受保护。

### Mirror 灾备接管

- 在模拟删除 A Worker、禁用 A 访问和丢失 A D1/R2 的情况下，B 能用离线恢复凭据重建控制面。
- 原域名绑定至 B 后，原文件路径和基于该域名的分享 URL 可继续使用。
- 接管前已确认的 `commitSequence` 数据无丢失；未确认事务不得出现在已保护状态中。
- 旧 A 恢复上线不能重新获得写权限，避免双主。
- 完整演练记录实际 RPO、RTO、DNS 生效时间和未完成上传行为。

## 12. 风险与约束

- Mirror 将应用层存储成本提高到约 2 倍，并增加跨账号写请求。
- 为实现接管，控制面同步必须与文件提交协议协同，否则可能出现“文件副本存在但目录没有”或相反。
- 分享密钥、节点密钥和恢复密钥迁移属于高风险安全功能，必须使用版本化密钥封装和轮换，不保存明文。
- Bucket Lock 可降低误删风险，但不能代替跨账号副本，也不能解决账号禁用。
- Stripe 归集依赖源节点在线，不能作为事后数据恢复手段。
- 在阶段 4 验收前，不应在产品界面宣称“主控账号失效后可无感接管”。

## 13. 最终边界

本次正式决策为：

- 实施 Stripe 与 Mirror 两种可选存储模式；
- Stripe 默认用于聚合容量，并提供受控节点归集到主控的能力；
- Mirror 使用两个跨账号实例提供数据双副本，并通过固定灾备恢复流程支持重新绑定域名后继续使用；
- 暂不实施类 RAID5/纠删码；
- 暂不实施任意主控与受控节点互换或自动选主。
